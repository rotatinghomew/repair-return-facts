# 事实仓模型与业务规则说明

## 1. 要解决的核心问题

售后整机退回、内部总成换装后，同一张凭证存在被双重使用的风险：

* 旧件既被拿去上游保修商处追偿一次；
* 又被当成用户机上仍然有效的质保对象继续使用。

根因是销售、生产装配、维修三个系统的标识范围不同、事件时间不同、更正到达时间不同。
事实仓不回写任何源系统，而是每天把源数据**全量重算**为一组带双时间、可追溯、不可变追加的事实。

## 2. 标识与时间约定

### 2.1 标识分配范围

| 对象 | 编号 | 唯一范围 | 仓内表达 |
| --- | --- | --- | --- |
| 整机 | 整机序列号 | 全局，出厂后保持 | `dim_vehicles.serial` |
| 配件（内部总成） | 配件序列号 | **仅所属厂商内唯一** | `part_key = 厂商/配件号`，如 `V-A/SHARED-X` |

不同厂商下相同配件序列号是两个实物，装载层不会合并；同厂商内重复配件号直接拒绝入仓。

### 2.2 双时间（bitemporal）

每条事实同时保留两类时间：

* **业务时间（有效期）**：维修实际发生日、签收实际发生日、销售日。
  拆装更正回补到原维修日期——即更正到达后，业务有效期的起点不变。
* **系统时间（登记/到达时间）**：`recorded_at`，更正单取 `correction_received`。
  迟到数据只影响系统时间与重算结果，不允许改写业务历史。

归属区间统一为**左闭右开 `[valid_from, valid_to)`**：一段止于 11-10、另一段起于
11-10 的正常换装链不会被误判为重叠；`valid_to = null` 表示开放区间。

## 3. 事实表清单

| 事实 | 文件/键 | 粒度 | 说明 |
| --- | --- | --- | --- |
| 整机维表 | `dim_vehicles` | 一台整机 | 销售日（原机保护期起算来源） |
| 配件维表 | `dim_parts` | 一个限定配件 | 厂商、公开质保月数 |
| 归属事实 | `fact_ownership` | 配件 × 工单 × 修订 × 有效期 | 同件同机唯一、相撞待裁、修订血缘 |
| 实物事实 | `fact_physical` | 配件事件流 + 退回单 | 在途/签收独立事件时间，与归属解耦 |
| 权利事实 | `fact_rights` | 一台整机上的一条保障 | 原机保护期与换件保障并存，带来源与适用日 |
| 追偿事实 | `fact_claims` | 一张追偿单 | 状态机推导结果，保留源状态与原始回执 |
| 冲正事实 | `fact_reversals` | 一条收回/冲正 | 独立追加，不删除原始凭证 |
| 更正血缘 | `fact_lineage` | 一次修订 | 记录哪条更正改变了哪些可见事实 |

## 4. 关键业务规则

### 4.1 一个配件同一时间只归属一台整机

* 同工单多次陈述按 `revision` 取最新，旧陈述置 `superseded` 并原样保留；
* 不同整机的有效期**重叠且无裁决** → 双方均置 `disputed`，并给出
  `undetermined_windows`（未定归属窗口）；
* 网点查询整机权利时，未定窗口的权利标 `undetermined` 单列，**同一整机其他
  已明确对象的权利不受影响、照常可查**；
* 同整机首尾相接的换装链是正常流转，不构成冲突。

### 4.2 迟到在途流水不能推断位置

* 实物位置只由退回/签收事件决定，与拆装陈述完全解耦；
* `in-transit` 永远不会因为入仓晚、或出现新工单，而被推断为“已装回/已签收”；
* 只有 `received` 且带 `received_at` 才生成 `factory_receipt` 事件。

### 4.3 质保权利跟随实际装入的件

两类权利共同适用、互不替代，每条都带来源与适用起止日（末日含）：

* `vehicle_base`：销售日 + 公开原机保护期（缺省 36 个月，可由源数据 `rules` 覆盖）；
* `replacement_part`：装入维修日 + 该配件厂商公开的 `warranty_months`；
* `superseded` 的归属段不产生当前权利——更正换装对象后，当前质保不再挂错件；
* 运行日只决定 `status_as_of_run`（active/expired/undetermined），不改变事件事实。

### 4.4 追偿状态机

```
工单完成、旧件在途            → pending_verification（待核追偿，可先生成）
在途 + 两工单争认同一旧件      → manual_review（留待人工确认）
厂方签收且与工单证据吻合       → eligible_to_settle（可交厂结算）
源端已接收/结算且证据吻合      → settled
更正换装对象、追偿未被厂方接收 → withdrawn（收回，追加 claim_withdrawal）
更正换装对象、凭证已被厂方接收 → reversed（追加 claim_reversal，原始回执保留）
厂方签收但与工单证据不吻合     → manual_review
```

证据吻合要求**同配件 + 同工单**：其他工单对同一配件的签收单不能拿来充数。
“争认”只在两张工单的归属窗口业务时间重叠时成立；先后换装（窗口首尾相接）不算争认。

### 4.5 更正与冲正的不可变处理

* 冲正/收回在**更正到达日**生效（无到达日才回退运行日）；
* 已被厂方接收的凭证不删除、不改写，只追加一条独立冲正事实，并保留
  `original_receipt`（如 `VENDOR-ACK-601`）；
* `fact_lineage` 把修订前后的整机、回补的业务日期、到达时间、关联冲正单号连成链，
  网点与对账岗可从一次换装追到“之后哪条更正改变了看到的事实”。

## 5. 每日可重跑

* `warehouse.pipeline.run(raw, run_date)` 是纯函数：同输入、同运行日必然得到
  完全相同的事实仓（测试以序列化结果断言）；
* 全量重建、无增量 upsert，重复重跑不会累积行；
* 落地方式为整体覆盖输出 JSON，可安全放进每日调度：

```bash
python3 -m warehouse.pipeline \
  --input data/extended_facts.json \
  --output out/warehouse.json \
  --run-date 2026-11-23
```

## 6. 查询视图（`warehouse.Serving`）

| 方法 | 面向角色 | 回答的问题 |
| --- | --- | --- |
| `part_trace(part_key)` | 网点/对账 | 一次换装的归属、权利、在途/结算位置、追偿、更正血缘 |
| `vehicle_warranties(vehicle, day)` | 网点 | 当前/指定日的明确权利与未定权利（分开返回） |
| `vehicle_parts(vehicle)` | 网点 | 整机上当前有效的质保对象（排除 superseded） |
| `claim(id)` / `reversals_for_claim(id)` | 对账岗 | 追偿状态、证据、原始回执与冲正单 |
| `claims_awaiting_action()` | 对账岗 | 待核/待人工/可结算三个工作桶 |
| `changes_affecting_work_order(wo)` | 双方 | 哪条更正、何时到达、改变了什么 |
